# Домашняя работа к занятию «Микросервисы: подходы»

## Задача 1: Обеспечить разработку

Для обеспечения процессов хранения кода, непрерывной интеграции (CI) и непрерывной поставки (CD) предлагается гибридная схема на базе платформы **GitLab SaaS** с использованием **собственных GitLab Runners**, размещенных в корпоративном контуре.
  
| Требование | Статус | Реализация в GitLab CI/CD |
| :--- | :---: | :--- |
| **Облачная система** | 🟢 | **GitLab SaaS** выступает в качестве единой управляющей панели и хостинга репозиториев без затрат на администрирование Control Plane. |
| **Система контроля версий Git** | 🟢 | Полная нативная поддержка Git, интеграция с SSH/HTTPS, защита веток (Protected Branches) и механизмы Code Review. |
| **Репозиторий на каждый сервис** | 🟢 | Изолированная структура проектов (Repositories) в рамках единой организации (Group/Subgroups) компании. |
| **Запуск сборки по событию из СКВ** | 🟢 | Автоматический старт пайплайнов через Webhooks по событиям: `push`, `merge_request`, `tag`, или изменениям конкретных путей (`changes:`). |
| **Запуск сборки по кнопке с параметрами** | 🟢 | Ручной запуск через GUI (`Run Pipeline`) с поддержкой пользовательских переменных типа `select`, `string` или `boolean`. |
| **Привязка настроек к сборке** | 🟢 | Динамическое задание переменных окружения (`variables`) на уровне запускаемого пайплайна или отдельных стадий (`stages`). |
| **Шаблоны конфигураций сборок** | 🟢 | Механизм `include:` позволяет переиспользовать единые централизованные CI-шаблоны (`template.yml`) для всей компании. |
| **Безопасное хранение секретов** | 🟢 | Защищенные и маскируемые переменные (**Protected & Masked CI/CD Variables**), а также интеграция с **HashiCorp Vault** через JWT-токены. |
| **Несколько конфигураций из репозитория** | 🟢 | Поддержка родительских и дочерних пайплайнов (**Parent-Child Pipelines**) и правила `rules:` для разделения сборок (e.g., App vs Infra). |
| **Кастомные шаги при сборке** | 🟢 | Секции `before_script`, `script`, `after_script` позволяют исполнять произвольные Bash/Python/Make сценарии. |
| **Собственные Docker-образы сборок** | 🟢 | Директива `image: registry.example.com/builder:latest` изолирует окружение сборки с использованием собственного Container Registry. |
| **Агенты на собственных серверах** | 🟢 | Развертывание **GitLab Runner** (Kubernetes Executor / Docker Executor) внутри собственного закрытого контура компании. |
| **Параллельный запуск сборок** | 🟢 | Горизонтальное автомасштабирование пула раннеров в Kubernetes (KEDA / HPA) для параллельной обработки множества пайплайнов. |
| **Параллельный запуск тестов** | 🟢 | Ключевое слово `parallel:` и матричные конфигурации (`parallel: matrix`) для автоматического параллельного распараллеливания тестов. |


Исходя из предъявленных требований GitLab является идеальным кандидатом.


## Задача 2: Логи

## 📋 Таблица соответствия требованиям

| Требование | Статус | Реализация в PLG-стеке (Promtail/Loki/Grafana) |
| :--- | :---: | :--- |
| **Централизованный сбор логов** | 🟢 | **Grafana Alloy** разворачиваются на каждом узле/хосте в виде `DaemonSet` и собирают логи со всех имеющихся контейнеров и приложений в единое хранилище **Grafana Loki**. |
| **Минимальные требования (`stdout`)** | 🟢 | Приложениями не используются специфические SDK или сторонние библиотеки — логи считываются агентами напрямую из потоков `stdout`/`stderr` контейнерного рантайма. |
| **Гарантированная доставка логов** | 🟢 | Агенты сборки используют локальный буфер (WAL/positions file) и механизм повторных попыток (backoff/retry), что исключает потерю логов при кратковременных сбоях сети или хранилища. |
| **Поиск и фильтрация** | 🟢 | Выполнение поиска с помощью языка **LogQL**: фильтрация по меткам, подстрокам, регулярным выражениям (`|~`), парсинг JSON/KeyValue «на лету» без предварительной сложной схемы. |
| **Пользовательский интерфейс и RBAC** | 🟢 | Доступ предоставляется через единый веб-интерфейс **Grafana Explore**. Разграничение прав (RBAC) позволяет ограничить доступ команд разработки только к их пространствам имен (namespaces/services). |
| **Прямые ссылки на сохраненный поиск** | 🟢 | Все параметры текущего поиска (временной интервал, текст LogQL-запроса, выбранные метки) кодируются в **URL-адресе страницы**, что позволяет делиться точным результатом поиска по ссылке.

Высокая экономическая эффективность, стандарт разработки для Kubernetes, единая экосистема наблюдения делает этот стек логирования приоритетным в моем выборе и согласуется с требованиями.

## Задача 3: Мониторинг


## 📋 Таблица соответствия требованиям

| Требование | Статус | Реализация в Prometheus-стеке |
| :--- | :--- | :--- |
| **Сбор метрик со всех хостов** | 🟢 | **Prometheus Server** в связке со встроенным механизмом Service Discovery (Kubernetes SD, Consul SD, File SD) автоматически обнаруживает и опрашивает все имеющиеся узлы и хосты. |
| **Метрики ресурсов хостов (CPU, RAM, HDD, Network)** | 🟢 | Развертывание **Node Exporter** на каждом виртуальном или физическом сервере для съёма системных метрик Linux/Windows OS в реальном времени. |
| **Метрики ресурсов контейнеров/сервисов** | 🟢 | Использование **cAdvisor** (встроен в kubelet в Kubernetes) для получения точной статистики по потреблению CPU, RAM, Disk I/O и Network сквозь призму отдельных контейнеров и подов. |
| **Специфичные кастомные метрики сервисов** | 🟢 | Микросервисы предоставляют эндпоинт `/metrics` с использованием официальных клиентских библиотек Prometheus (Go, Java, Python, Node.js). Сбор бизнес-метрик (RPS, Latency, количество ошибок, размер очередей). |
| **Запросы и агрегирование (Ad-hoc UI)** | 🟢 | Язык запросов **PromQL** в веб-интерфейсе **Grafana (Explore)** или Prometheus UI позволяет выполнять агрегации любой сложности (`rate`, `sum`, `histogram_quantile`, `avg_over_time`). |
| **Интерфейс и настраиваемые панели** | 🟢 | **Grafana UI** предоставляет гибкий конструктор дашбордов с различными типами визуализаций (Graph, Stat, Heatmap, Gauge), переменными для динамической фильтрации и системой шаблонов. |

Экосистема готовности из коробки, понятная и контролируемая модель сбора данных (Pull Model), мировой золотой стандарт в мониторинге и отвечает установленным требованиям.
